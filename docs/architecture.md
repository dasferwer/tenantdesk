# Архитектура TenantDesk

## Граница доверия

JWT определяет глобальную учётную запись. `X-Tenant-ID` выбирает контекст,
но сам по себе не разрешает доступ: API проверяет membership и роль.
`set_config('app.tenant_id', value, true)` и `app.actor_id` действуют только
в текущей транзакции. Commit/rollback убирает значения перед возвратом
соединения в пул. Yield dependency завершается до отправки HTTP-ответа.

RLS доверяет контексту, установленному backend. Она защищает от пропущенного
фильтра в прикладном запросе, но не от полного захвата процесса или возможности
выполнять произвольный SQL с изменением session settings. SQL в сервисе
параметризован; конечные пользователи не получают доступ к PostgreSQL.

## Политики

На документах, редакциях, приглашениях, аудите и экспортах включены ENABLE и
FORCE ROW LEVEL SECURITY. USING и WITH CHECK сравнивают tenant_id с локальным
контекстом. Без контекста строки невидимы, запись в чужую компанию запрещена.
Составные внешние ключи связывают редакции и документы одной компании.

Глобальные users обслуживают аутентификацию. Для списка собственных организаций
есть отдельные SELECT-политики self-discovery на memberships и tenants,
завязанные на `app.actor_id`. Это намеренное исключение для метаданных членства;
оно не открывает содержимое документов других выбранных контекстов.

| Роль PostgreSQL | Полномочия |
|---|---|
| tenantdesk_owner | Только bootstrap/migrate; владелец схемы |
| tenantdesk_app | API, ограниченные DML, SELECT/INSERT истории; нет чтения export_outbox |
| tenantdesk_worker | Чтение очереди ID, чтение документов через RLS, завершение экспорта и INSERT аудита |

Worker имеет UPDATE(id) на tenants и UPDATE на outbox для row locking.
Он не читает users. Роли API/worker не superuser и не BYPASSRLS. При старте API
дополнительно отказывается работать владельцем таблиц. Роли создаёт скрипт
в отдельном PostgreSQL-образе; пароль мигратора не передаётся API.

## Конкурентность и версии

Изменения внутри компании берут её строку FOR UPDATE. После ожидания
блокировки membership проверяется повторно: отозванное членство не разрешает
отложенную запись. В этой же транзакции проверяются квота и версия документа,
сохраняются данные, редакция и аудит. Это сериализует изменения одной компании,
что является осознанной границей масштабирования учебного проекта.

`version` увеличивается при изменении содержимого, удалении и восстановлении.
Редакции хранят только изменения содержимого, поэтому их номера могут иметь
пропуски после удаления/восстановления. Старый `If-Match` возвращает `409`.
Квота storage включает UTF-8 байты заголовка и тела каждой сохранённой редакции.

## Фоновый экспорт

API атомарно создаёт RLS-защищённый job и outbox из двух UUID: tenant/job.
Worker получает кандидатов, устанавливает tenant-контекст, блокирует tenant,
outbox и job, повторно проверяет членство инициатора и делает SELECT документов
через собственную ограниченную роль. Запись снимка, аудит и удаление outbox
коммитятся вместе. Падение до commit откатывает всё и оставляет задание для повтора.
Отзыв доступа до начала обработки завершает job как rejected без данных.
Экспорт отражает состояние на момент обработки, а не запроса.

Фоновые задачи не выполняют внешних эффектов: JSON хранится в той же БД,
поэтому здесь достаточно одной транзакции. Запущенные и авторизованные чтения
могут завершиться после начала отзыва доступа; новые запросы проверяются заново.

Справка: [PostgreSQL Row Security Policies](https://www.postgresql.org/docs/17/ddl-rowsecurity.html).
