# Как объяснить TenantDesk на интервью

**Задача:** компании используют один backend и одну БД, сохраняя изоляцию данных.

**Путь запроса:** JWT → выбор компании → проверка membership → SET LOCAL
tenant context → прикладные запросы → PostgreSQL RLS → commit до HTTP-ответа.

**Главные решения:** RLS как дополнительная защита от пропущенного фильтра,
раздельные роли мигратора/API/worker, транзакционный контекст без утечки через пул,
квоты под блокировкой компании и optimistic concurrency для документов.

**Что показать:** прямой SELECT без WHERE tenant_id от роли приложения;
тест повторного использования того же PostgreSQL соединения; viewer, который
читает, но не пишет; восстановление документа; экспорт, не содержащий данные
другой компании; отклонение экспорта после отзыва членства.

**Компромиссы:** RLS доверяет backend-контексту, а не защищает от захваченного
DB-пользователя. Мутации одной компании сериализованы. Экспорт ограничен по
размеру и хранится в PostgreSQL; для больших вложений следующим этапом был бы S3.

Корректное описание: «Создал портфолио-SaaS с tenant isolation, RLS,
версиями документов и проверками изоляции API и фоновых задач».
